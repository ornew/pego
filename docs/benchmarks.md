# Benchmarks

This document records the performance of the PEGO backends (closure, recursive and iterative bytecode VMs, and Go parsers generated by `pego gen`) and, where a comparable parser exists, of the corresponding Go standard-library parser. The benchmark plan is in [design record 010](design/010-bytecode-vm.md#performance-comparison). For the history of individual optimizations, see [performance.md](performance.md).

```bash
go test ./bench -run '^$' -bench . -benchmem -count 3
```

`TestWorkloads` in `bench/` checks, on reduced inputs, that every input can be parsed by every backend and that the PEGO backends return the same results.

## Method

- Inputs are generated by `bench/inputs.go` from a fixed random seed, so they are identical across runs. They include multi-byte characters such as Japanese text.
- The grammars are taken unchanged from `examples/`: JSON, CSV, XML, the calculator in its Pratt and left-recursive forms, minilang, and outline.
- Each benchmark runs three times and the median is reported. Measurements vary between runs by a few percent on an idle machine, and by 10–20% on a shared one.
- The factor in parentheses is the time relative to the closure backend with the same position unit (lower is faster).
- Comparisons with the standard library measure different outputs. Every PEGO backend builds a typed tree whose nodes carry positions (start and end) and rule names, and records the expectations at the farthest failure. The standard-library parsers produce:
  - `encoding/json`: decoding into `any` (no positions).
  - `encoding/csv`: `ReadAll` (a list of field strings with quotes removed).
  - `encoding/xml`: reading tokens with `Decoder.Token` (no tree).
  - `go/parser.ParseExpr`: a Go expression AST (with positions).

| Workload | Grammar | Input | Main focus |
|:--|:--|:--|:--|
| JSON | `examples/json` | Array of objects, about 260 KB | Lexical repetition, AST of union types |
| CSV | `examples/csv` | 5,000 rows; fields with quotes, commas and newlines | Simple repetition, many terminals |
| XML | `examples/xml` | Nesting, attributes, character references, comments, CDATA; about 260 KB | Nesting, a predicate comparing start-tag and end-tag names |
| Arith_Pratt | `examples/calculator/calc.pego` | Expression with 20,000 terms, parentheses nested up to depth 40 | Pratt loop and longest match |
| Arith_LeftRec | `examples/calculator/calc_lr.pego` | Same as above | Left-recursion seed growing |
| Minilang | `examples/minilang` | 300 functions | PEG statements nested with Pratt expressions, keyword exclusion |
| Recovery | `examples/minilang` | Same as above, with one line in seven broken | `#recover`, expectation recording |
| Outline | `examples/outline` | 5,000 lines, depth up to 10 | Predicates and variables (non-memoized rules) |
| Incremental | `examples/minilang` | Repeated one-character insertions and deletions in 300 functions | Memo reuse with `Document` (compared with a full parse each time) |
| Stream | `examples/csv` | 50,000 rows (about 2.2 MB) | Reading and discarding with `ParseStream` |
| Prepare | JSON, minilang | None | Compiling from source and loading `.pegoc` (with and without the AST) |

## Results

Measured on 2026-10-08 at commit 2e688c7 with Go 1.27.1 on an Apple M3 Max (16 cores), with no other load.
Times are per parse (median of 3 runs); factors in parentheses are relative to the closure backend.
Earlier versions of this document were measured on a 4-vCPU Intel Xeon virtual machine, so their numbers are not
comparable with these. For the history of the optimizations behind these numbers, see [performance.md](performance.md).

## Analysis

- **Generated Go parsers are the fastest backend**, 13–33% faster than the closure backend (0.67–0.87×). Since the
  allocation work of performance.md changes 14–37, every backend allocates about a thousand objects per parse on most
  workloads (a few times more than the standard-library parsers' bytes, but far fewer objects).
- **The bytecode VMs are 1.1–1.4× (recursive) and 1.2–2.0× (iterative) slower than the closure backend.** The
  iterative VM pays for running rule calls and Pratt loops as state machines on its own stack.
- **The standard library remains 3–8× faster than generated parsers** (4–12× than the closure backend). The
  comparison is not like for like: `encoding/json`, `encoding/csv` and `encoding/xml` build no positioned typed tree,
  and `go/parser` uses a hand-written lexer.
- **Recognition** is 1.2–2.0× faster than a full parse on the closure backend. It is still far from `json.Valid`, a
  hand-written state machine.
- **The position unit makes little difference**; byte positions are a few percent faster.
- **Incremental parsing** is about 15× faster than a full parse after a one-character edit and allocates about a
  seventh as much.
- **Streaming** runs at about two thirds of the throughput of batch parsing while holding only its working set (memory
  does not grow with the input).
- **Loading `.pegoc`** takes roughly 1/2 to 1/6 of the time of compiling from source; files without the AST are the
  fastest to load and the smallest.

## Default backend

The default backend (`pego.DefaultBackend`) is the **closure backend** when the grammar AST is available, and the **recursive bytecode VM** when it is not (a `.pegoc` file saved without the AST). The reasons are:

- Within a Go process, the closure backend is faster than bytecode on every workload (by 10–40%).
- Bytecode is a portable format; there is no reason to prefer it inside Go. A file without the AST cannot be turned into closures, so bytecode is used for it.
- The iterative VM is selected explicitly when deeply nested input must be parsed independently of the Go stack size.
- Generated Go parsers are the fastest; use them when the grammar is fixed.
